## 3. 状態の移り変わり

```
原資料：new ─AIが下書き─→ drafted ─経理が保存─→ confirmed
         └─対象外（理由）─→ ignored
仕訳：  draft ─経理が保存＝確定─→ confirmed ─社長が戻す（理由）─→ returned ─経理が直して保存─→ confirmed
AI：    waiting → reading（ai_stage）→ done / failed
帳票：  reading → review（経理が確かめる）→ saved / failed
```

**「あと n 件」＝全期間の `source_records.status = new` ＋ `journal_entries.status IN (draft, returned)`**（`RemainingCount` だけで数える。下書きのある原資料は仕訳側だけで数える）。前月以前の日付の未処理件数も併記し、月をまたいだ下書きが残っているのに完了と誤表示しない。

## 4. 処理（Services）

どれもトランザクションの中で、対象の行を `lockForUpdate()` してから状態を確かめる。監査記録もトランザクションの中。

### 4.1 SubmitEvidence（F04・F05、まとめて送る）
- 画面は、撮るたびに一時ファイル（Livewire の `WithFileUploads`、`photos[]`）をためる。「まとめて送る（n枚）」で、同じ `batch_id` を付けて1枚ずつ `submit()` を呼ぶ（既存の処理をそのまま使う）。
- 結果を1枚ずつ返す：送れた／もう届いています。1枚でも送れたら「送れました（n枚）」。

### 4.2 ProcessEvidenceWithAi（F06、実装済み）
読み取り → 仕訳の下書き → 検算。版3.0 で足すこと：検算の結果から `concern_flags` の AI の印（ai_duplicate・ai_private・ai_unbalanced）を入れる。
- L1（`read_receipt.v3`）は `amount_missing`（金額がそもそも書かれていない）と `payment_method`（cash / card / invoice_later / unknown）、宛名 `addressee` とその種類 `addressee_kind`（入力の会社名と比べる）も返す。
- L1 の日付は `ReadingChecks::validReceiptDate` で `YYYY-MM-DD`・実在日・今日以前を確かめてから原資料に保存する。不正・和暦・未来日は原資料を `null` にし、仕訳の日付は今日にする。
- L2（`journalize.v3`）は分類と支払い元（口座の名前）だけを返し、**借方・貸方の行はコードが組む**（`JournalLineWriter`）。支払い元は、①同じ店の**確定履歴**が十分にそろっているとき（`EntryRecommender`、§4.3a）その支払い元 ②`invoice_later` なら「後日の請求」の口座 ③AI が選んだ口座 ④既定の口座、の順。①のときは画面に「過去の確認（同じ店 n 件）から『○○』にしました」（`ai_check.remembered_payment`）。履歴が足りない・食い違うときは当てず、参考の候補として出す。
- L2の分類・口座は会社内の有効な名前を `enum` にする。旧名・使用停止名を直し後に持つ例は件数制限の前に除き、直し前だけが旧名の例は `before`・`kernel` を入力から外す（履歴自体は保持）。選択肢外の応答は1回だけ再試行し、2回失敗したら下書きを保存しない。再生記録も現在のスキーマで検証し、不適合なら再利用せず通常のAI処理へ戻す。
- 設定からの分類名変更は会社をロックして処理し、同じ会社の有効な分類との重複を拒否する。他社・使用停止済みの分類は重複判定に含めない。既存データに同名の有効分類が複数ある場合、下書き作成は理由を示して止め、最初の1件の勘定科目を選ばない。
- **金額の記載がない書類**（ガソリンカードの納品書など）は、行のない下書きを作り、`amount_missing` の印を付ける。検算（L3）は呼ばない。経理が金額を入れたら確定できる（記載のなかった金額を入れたのは「直した」に数えない）。
- 常駐は2つ（`torudake-queue@1`・`@2`）。`retry_after`（300秒）はジョブの時間の上限（240秒）より長くする。
- ジョブが最終失敗したら `failed()` で会社スコープ・行ロックを使い `ai_status=failed` にする。`waiting`・`reading` が10分以上更新されない原資料も5分ごとの定期処理で失敗に戻す。エラー内容を `ai_error` に残し、経理が手入力して「次へ」へ進める。通常の例外は技術情報を画面に出さず、AI固有の説明だけを出す。

### 4.3 ConfirmEntryService（F07、経理の保存＝確定）
```php
DB::transaction(function () use ($company, $user, $entryId, $input) {
    $entry = $company->journalEntries()->lockForUpdate()->findOrFail($entryId);
    if ($entry->status === EntryStatus::Confirmed) return $entry;              // 2回押しても1回だけ
    // 直した欄ごとに ai_corrections（前後・理由・kernel）を入れる
    // 行を作り直す（支出：借方＝分類の勘定科目、貸方＝支払い元の口座の勘定科目）
    $flags = $this->concernRules->for($entry, $company, corrected: $wasCorrected);  // §4.5
    $entry->forceFill([
        'status' => EntryStatus::Confirmed, 'confirmed_by' => $user->id, 'confirmed_at' => now(),
        'concern_flags' => $flags, 'returned_reason' => null,
    ])->save();
    $entry->sources()->lockForUpdate()->get()
        ->each(fn ($s) => $s->forceFill(['status' => SourceStatus::Confirmed])->save());
    AuditLog::record($user, 'entry.confirm', $entry);
});
// トランザクションのあとで：WorkbookService::upsertRow($entry)（§4.6）、気になる印があれば社長へ通知（§4.8）
```
- 保存の前に、規則の検算（借方合計・貸方合計。コードが保存されている最新の行から円の整数で計算）とAIの気になる点を、別の欄で必ず画面に出す（守り §01-6.2）。AIが答えた貸借（`ai_check.balanced`）は過去の回答として残すだけで、表示・印・保存の可否には使わない。
- **貸借が一致しない・行が不正な仕訳は確定させない（版3.1・実務用の仕様。デモの「止めない」から変更）**。保存のトランザクション内で行を書き直したあと、最新の行を `JournalBalanceChecker` で検算し、問題があれば例外でトランザクションごと戻す（仕訳・原資料・直した記録・Excel・監査に何も残さない）。社長から戻された仕訳の再確定でも同じ。問題の種類：行なし／借方か貸方のみ／借貸が不正／1円未満・整数でない／範囲外（1行 1,000億円・合計 1兆円まで）／合計不一致。
- 金額の記載がない下書き（行なし）は「検算していない」と表示し、不一致とは言わない。保存には金額が必要（行を書いたあとの検算で確かめる）。
- 貸借が合っていても、科目・税率・取引内容が正しいとは限らない。画面にもそう書く。

**読み取りの確認（版3.2・#51）**：AI が読んだ値と、読めず補った値と、人が確かめた記録を分ける。
- `journal_entries.reading_review`（json）に、下書きを作るときの欄ごと（日付・店名・金額）の由来を残す：`read`（AIが読んだ）／`defaulted`（日付が欠落・形式不正・存在しない日・未来日で、今日の日付を仮に入れた。理由は `missing`・`invalid`・`future`）／`missing`（読めなかった）。原文は `ai_runs` を参照し、複製しない。AI が読めず人が最初から入れる下書きは、日付が `defaulted`、店名・金額が `missing`。
- 要確認の理由は欄ごとに別に出す：`date_missing`／`date_invalid`／`date_future`／`vendor_missing`／`amount_missing`／`low_confidence`（合計 0.8 未満、日付・店名 0.7 未満。ちょうど閾値は低くない）／`confidence_unknown`（自信度が欠けている・0〜1 の範囲外・数字でない。「確認不要」とは扱わない）。AIの自信度は正解率ではなく、高くても読み違いはあり得る（画面にもそう書く）。画像上の位置は持っていないので、文字の位置を示す枠は出さない。
- **保存を止める範囲（本人の決定 2026-11-08）**：AIが読めず補った日付（`defaulted`）だけ。人が日付を直すか「写真を見て、この日付でよい」にチェックしないと保存（確定）できない。低い自信度・自信度不明・店名や金額の欠落は、表示するだけで保存は止めない（金額は従来どおり入力が必須）。自信度だけで全欄を確認済みにも自動確定にもしない。
- **確認の記録**：保存のトランザクション内で、要確認の理由があった欄ごとに `reading_confirmations`（会社・仕訳・ai_run・欄・method・理由・保存した値・保存した人・日時）を1行ずつ残す。method：`confirmed`（確かめた）／`changed`（人が直した）／`entered`（AIが読めず人が入れた）／`saved_as_is`（注意が付いたまま保存）。元の警告と「人が確認した」は別の情報。値や読み取りの版が変われば新しい行になり、戻された仕訳の再確定ではもう一度確かめる（前の確認は使い回さない）。確定済みへの2回目の保存・後着のAIは記録を増やさず、`reading_review` も変えない。`entry.confirm` の監査記録にも欄ごとの method を残す。
- 操作の権限は既存の `editDraft`（原資料の詳細を開いて保存できる人）と同じ。新しい権限・一括承認・自動確定は作らない。ライブ画面の S（そのまま保存）は、仮の日付のとき止まり、理由と「直して確定」の画面への道を出す。
- #32（測定）には、`ai_corrections`（直した欄）と `reading_confirmations`（method）を渡す。
- **初回確定の記録（#32）**：`first_confirmations`（1仕訳に1行、書き換え・削除不可）。初回確定のトランザクション内で、種類（`ai`／`manual`）・評価の分類（`real`＝実際のAI（claude）かつ実際の会社／`demo`＝fake・replay・デモ会社）・L2 実行ID・driver・prompt_version・必須項目の充足・AI の値を変えた欄（`changed_fields`）・記載がなく人が埋めた欄（`filled_fields`）・摘要を直したか・下書きの値の由来（日付・店名・金額の読み取り、分類＝AI、支払い元＝`history`（同じ店で直した履歴）／`invoice_rule`／`ai`／`default`）・読み取りの確認の方法・重複候補の件数と判断済み件数・直した理由・初回確定の人と時刻を残す。戻し・再確定は `entry_post_events`（`returned`／`reconfirmed`、変わった欄）に別に残し、初回の記録は変えない。履歴・規則由来の値を、AI 自身の答えと混ぜない（`journal_entries.draft_payment_origin`）。
- **履歴からの推薦（§4.3a・#54）**：同じ店の確定履歴から分類・支払い元の候補を出す。根拠は**この会社の人が確定した仕訳**だけ（他社・AI の案・下書きは使わない）。`journal_entries.vendor_key`（正規化した店名。`App\Support\VendorKey`、保存のたびに入る）の索引で同じ店を引き、件数の上限で同じ店が範囲外にならない。分類・口座は ID で数え、使われていない（archived）ものは候補にしない。
  - **confident**（下書きの支払い元に当ててよい）：確定が2件以上（`EntryRecommender::MIN_CONFIRMED`）で、使い方が一つにそろい（多数派が8割以上で直近もそう）、最後の確認が180日以内で、後日請求と食い違わず、戻された仕訳がない。
  - **hold**（参考として出し、自動では当てない。理由を画面に出す）：履歴が1件だけ（`few_history`）・古い（`stale`）・使い方が分かれている（`mixed_usage`、最大3候補）・後日請求なのに過去は別の支払い元（`payment_conflict`）・同じ店に戻された仕訳がある（`returned_in_history`）。**none**：使える履歴がない（`retired`＝分類・口座が使われなくなった、を含む。失敗ではない）。
  - 下書きには `journal_entries.recommendation`（元の AI（L2）の案・履歴の候補とその根拠の仕訳 ID・当てたか）を残す。画面の「過去の確認から」は開くたびに引き直し、経理が「今回も使う」（欄に入れるだけ。確定にしない）・別を選ぶ（欄を直す）・「保留にする」を決める。ライブ画面は表示だけ。操作の権限は `editDraft`（直して確定と同じ）で、新しい権限はない。
  - 保存のとき、候補を最新の履歴で確かめ直し、`first_confirmations.recommendation` に扱い（`adopted`／`rejected`／`held`／`no_candidate`）と、下書きのときの根拠が変わったか（`expired`）を残す。根拠にした仕訳が戻された・直された場合は、画面に警告を出し、下書きは自動では変えない。
  - 測り方：AI の記録画面に、採用・別を選んだ・保留・採用後の事後修正・失効・候補なしを並べる。採用率だけで改善とは言わない。確認時間は #44 の実作業計測まで未計測（`review_seconds` は null）。書き出しの `first_confirmations.jsonl` には状態・理由の型・件数・扱いだけを出す（分類・口座・店名は出さない。schema_version 4）。
- **指標の定義の正本は `App\Support\FirstConfirmationMetrics`**（版 `first-confirmation.v1`）。画面（AIの記録）・書き出しの manifest・JSONL から数え直した値が、同じ母数・分子になる。母数は「その月に初回確定した、AIが下書きを作った仕訳」で、再確定・戻しでは増えず月をまたいで二重に数えない。「手を入れず確定」は、日付が読めて金額の記載があり、日付・店名・分類・支払い元・金額を変えず、記載のなかった欄も埋めていないこと。摘要は自由文なので含めず別に数える。実際のAIとデモ・fake は混ぜない。記録のない過去の確定は「評価不能」として件数だけ出し、率に入れない（母数0は0%にも100%にもしない）。**正解率ではなく、下書きに手を入れたかという行動の数字**で、会計上の正しさは別途、人が検証したラベルのある評価集合でだけ測る。
- 推薦（#54）の採否は、#54 の実装時に同じ初回確定の記録へ足す（今は支払い元の「履歴」の反映だけを区別する）。

**二重計上の候補（版3.3・#53）**：撮り直し・別ファイル（hash が違う）の同じ取引を、コードで探して根拠つきで見せる。AI は使わない。完全な重複検出ではなく、不正の検知でもない（誤警告もある）。
- **探す範囲（本人の決定 2026-11-08）**：同じ会社の仕訳のうち、**日付が前後7日**・**借方の行の金額が同じ**もの。状態は下書き・確定・社長から戻しを含め、**対象外にした原資料は含めない**。金額がまだない下書きは探さない。件数は黙って切らない。表示は1件の原資料につき**5件まで**、超えた分は「ほか n 件」と件数で出す。
- **一致の条件**（`DuplicateCandidateMatcher`。同じ入力なら同じ結果）：店名は全角半角・空白・「株式会社/(株)」などをそろえて比べる。**確かな一致**＝金額・日付・店名がすべて同じ。**近い一致**＝店名が同じで日付が1〜7日ちがい、または同じ日で一方の店名がもう一方を含む（短いほうが3文字以上）。**ゆるい一致**＝店名が片方か両方わからない／日付ちがいで店名が似ている。店名がまったく違うもの、**収入（返金）と支出の組み合わせ**は候補にしない。
- **AIが読めず仮に入れた日付（未確認）は、確かな一致にしない**（ゆるい一致で「日付が未確認」と根拠に書く）。請求書（未払金）と支払い済みの領収書の組み合わせは、根拠に「請求書と領収書かも」と書く。証憑番号は、原資料に保存していないので使わない。
- **印**：強い・近い一致の候補があり、「別の取引」と判断されていなければ、保存時に気になる印 `duplicate_candidate`（二重計上の候補あり）を付ける。ゆるい一致は表示だけ。AIの `duplicate_suspected`（`ai_duplicate`）は「AIの参考」として別の印のまま残し、AIだけでは対象を断定しない。
- **判断（本人の決定）**：候補があっても**保存は止めない**（同じ日・店・金額の別取引を自動で拒否しない）。経理は候補ごとに「別の取引」「重複なので今回を対象外」「保留」を記録できる（理由は「別の取引」「対象外」で必須）。「対象外」は既存の `IgnoreSourceService` を使い、**確定した原資料は対象外にも判断にもできず、確定済みの仕訳は取り消さない**。
- **記録**：`duplicate_reviews` に、判断・強さ・根拠・理由・判断した人と日時と、**判断した時点の対象と候補の値（fingerprint）**を残す。値が変わったら古い判断は使わず、もう一度判断が要る。判断の直前と保存の直前にも、最新の値・最新の候補で照合し直す（候補が変わっていたら記録しない）。二重クリックで記録は増えない。`entry.confirm` の監査記録に、保存時の候補（上位10件）と判断を残す。
- 権限は既存の `editDraft`（原資料の詳細を開いて保存できる人）。送るだけの人は候補の一覧を見られない。候補・画像・仕訳は会社から引き、他社の候補IDは404。ライブ画面には、強い・近い一致の件数と「直して確定の画面で見比べる」だけを出す。
- #32/#44 には、`duplicate_reviews` の判断（誰が・どの強さの候補を・どう判断したか）を渡す。
- AI修正の記録・理由は初回のAI下書きの確定だけ。再確定では `ai_corrections` を追加せず、「経理がAIを直した」の印も新しく付けない。初回に付いた印は保持し、再確定の変更前後は `entry.confirm` の監査記録に残す。

### 4.6 WorkbookService（F14・F15、Excel の1冊）
- 1冊を `phpoffice/phpspreadsheet` で開き、`version` を確かめてから書く（同時に書いたら後から来たほうがやり直す）。
- **仕訳帳シート**（既定の列）：管理番号（仕訳の UUID 全体）・日付・取引先・分類・借方科目・借方金額・貸方科目・貸方金額・摘要・**状態**（確定／社長から戻し）・確定した人・確定した日時・AIのまま／直した
- 確定 → 行を足す（`workbook_row` に行番号）。戻す・再確定 → 同じ行を書き換える（UUID 全体の管理番号で探す）。旧形式の末尾8文字しかない既存行は、その番号が会社内の1仕訳だけに対応すると確かめられる場合にだけ再利用し、衝突の可能性があれば別行へ追加する。
- 仕訳帳の「直した」は、AI修正の記録・印に加え、会社内の `entry.confirm` 監査記録に残った人の変更でも判定する。再確定の変更を表示するためにAI修正の印を付けることはしない。
- 書くのは確定のトランザクションのあと。書けなくても確定は取り消さず、ダウンロードの前に行のない確定の仕訳を足す（`syncMissing`）。足す前に管理番号で探すので、二重にならない。ファイルがなくなったら作り直し、確定の仕訳をすべて入れ直す（DB が正。ファイルはバックアップしなくてよい）。
- ダウンロードのファイル名は `{会社名}_帳簿.xlsx`（日本語が使えない環境では `torudake.xlsx`）。
- **社長用シート**：三期比較の表（月×3期）、今期の登録済みの支出と参考差額。社長の画面と同じ数字・同じ定義（§4.7「数字の定義」。比較は両年そろった月だけ、参考差額には「現預金・利益ではない」「集計期間」「含めていないもの」を添える）。ダウンロードのたびに作り直す。
- **AIの記録シート**：AIの実行回数・直された回数・多い直し。
- 既存の Excel の取り込み（F15）：アップロードされたファイルの1行目を列の名前として読み、上の列と対応づける画面を出す。対応づけたら `layout` に保存し、以後その形で追記。**列の形が分かるまでは既定の形で作る。**

### 4.7 OwnerDashboard（F12、社長の画面の数字）
| 区画 | 数字 | 出どころ |
|---|---|---|
| ① ひとこと | 一番大きな変化を1つ・理由の見立て・確かめるとよい点 | `owner_brief`（AI）。渡すのは②⑤の合計と、月ごとの**忙しい月の印**・**3期の平均**・**忙しい月なのに前年同月より少ない**の印だけ |
| ② 三期比較 | 月×（今期・前期・前々期）の売上 | `external_monthly_figures`（sales） |
| ② 今期の登録済みの支出・参考差額 | 今期の月ごとの確定した支出（分類ごと）、参考差額（登録済みの売上 − 登録済みの支出） | アプリの confirmed の仕訳＋②の売上 |
| ③ 気になる仕訳 | `concern_flags` があり `owner_seen_at` が null の確定した仕訳（`app/Support/OwnerConcerns` だけで数える）。「見た」で `owner_seen_at` を入れる。数はサイドバーのバッジにも出す | アプリ |
| ④ 来月の見込み | 来月の売上と経費の中央値・8割の範囲 | `forecast`（AI）。過去の月の実績と、月ごとの忙しい月の印・3期の平均を渡す |
| ⑤ 売上の柱 | 上位3社の割合（A社・B社・C社） | `external_customer_sales` |
- 比べは**金額の差を主に、%を添える**。前月だけでなく**前年同月**と並べる。
- 前年同月の差は、その月に今期の数字があれば今期−前期、まだなければ前期−前々期（画面に「前期と前々期」と添える）。「忙しい月なのに前年より少ない」も同じ差で決める。
- 経費は、アプリを使い始めた月からしかない（過去の経費は財務王にあり、取り込まない）。経費のない月は「—」と出す。
- **数字の定義（#34。画面・Excel の社長用シート・AI の入力で同じ）**
  - **前期との比較**（`totals.diff`・`pct`）は、今期と前期の**両方に数字がある月だけ**を足して比べる。前期が欠けた月を0円とみなさない。実際の0円は数字として使い、欠けている月（null）と区別する。%は前期の合計が0のとき出さない。
  - 画面は「前期の同じ月（比べられる n か月）より …」と比較月の数を添え、比べていない月があれば「前期の数字がない n か月は、比べていません」と出す。比べられる月がなければ「前期と比べられる月はまだありません」。
  - 「今期の売上」の合計（`totals.current`）は、数字のある全月を足す別の指標。比較の合計（`comparable_current`・`comparable_previous`）とは別に持つ。
  - **参考差額**（`reference_diff`）＝登録済みの売上 − 登録済みの支出（確定）。売上か支出の片方がない月は出さない（欠けた方を0にしない）。**現預金の残高でも、利益でもない**（未登録の支出・入金、借入の返済、設備の購入などは入らない）。ラベルは「参考差額（売上 − 支出）」とし、「残ったお金」とは書かない。
  - 参考差額の下に、集計期間（今期の開始日〜終了日）、含めたもの（確定した支出の件数・最後の確定の日時）、含めていないもの（未確定の下書き・社長から戻した仕訳の件数）、集計時点を出す（`expense_info`）。
  - AI（`owner_brief`・`forecast`）には `totals` をそのまま渡し、プロンプトで「比較月の数を添える」「利益・もうけ・残ったお金・現預金と言わない」と決める（プロンプトの版：`owner_brief.v3`・`forecast.v2`）。
  - Excel の社長用シートは、この定義のまま作る（作る工程で、この節の `OwnerDashboard` の数字をそのまま使い、独自に計算しない）。
- ①④（`OwnerInsights`）：社長の画面を開くたびに入力（②③⑤の数字＝確定した仕訳を含む）のハッシュを出し、`owner_insights.input_hash` と同じなら AI を呼ばない。違えば `GenerateOwnerInsight` をキューに入れ、できるまで前回のものに「更新中」と出して2秒ごとに読み直す。頼んでから5分たっても終わらなければ頼み直す。AI が失敗したら前回のものを残し、5分は頼み直さない。デモの前に一度開いておけば、同じ数字のうちは待たずに出る。

### 4.9 ReportImportService（F16、帳票の取り込み）
1. 経理が帳票を撮って送る（種類を選ぶ：三期比較／顧客別）。写真は `evidences` に入れる（30日で消える）
2. `ProcessReportWithAi`：`read_report` で表を読む。三期比較なら「期・月・売上金額」の表、顧客別なら「期間・売上金額・返品・値引き」の列（**取引先の名前の列は読まない・保存しない**）
3. 経理が、読んだ表を画面で確かめて直す（数字の読み違いを直せる）→ 保存
4. 三期比較 → `external_monthly_figures`（月ごと）。顧客別 → 金額の大きい順に `external_customer_sales`（A社・B社…）
5. 監査 `report.import`

現在の月別売上画面では、開いたときに表示した取り込みIDを `#[Locked]` で固定し、その会社から取得して保存する。他の人が新しい取り込みを作っても対象を差し替えない。同時刻の取り込みはIDの降順で最新を決める。`review` だけ保存でき、保存済み・読み取り中・失敗の理由は画面の保存エラー欄に表示する。

TrainingDataExporter（JSONL）、PurgeExpiredEvidence（毎日3時）、Artisan コマンド（`torudake:create-company`・`torudake:add-member`・`torudake:seed-demo`）。`torudake:seed-demo` は、**架空の**三期比較（3期分の月ごとの売上。架空の基準額×季節の係数で作り、忙しい月の初期値と同じく**秋（10〜12月）が多く、6・7月もやや多い**形にする。デモの見せ場のため、忙しい月のうち1か月は前年同月より少なくする）・顧客別（上位2社で約8割）・今期の確定した経費・「あと1件」から始まるデータを入れる。人は作らない（§9）。
