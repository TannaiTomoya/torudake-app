# 10｜一次仕訳の蓄積・AIの学習・テスト環境から本番へ（設計案）

版0.2・2026-10-23（D1〜D3を決定。Anthropicの規約を確認）。本人承認で確定する。これまでの設計（07技術要件・08詳細設計・09証憑入口）の決定を変える箇所は「変更」と明記する。

## 0. 一言でいうと

**撮る → AIが仕訳の下書きを作る → 人が直して承認する → 直した理由をAIが次から使う。** 写真は1か月で消し、残すのは仕訳と学習データだけ。全部をテスト環境で確かめてから本番に出す。

## 2. 全体の流れ

```
[現場] 撮って送る
   ↓ 写真（30日だけ保存）
[AI] 日付・合計・店名・分類の候補を読む ← 会社ごとの「直した例」「ルール」
   ↓ 下書き（自信の低い欄に印）
[経理担当] 通帳の明細・現金と突き合わせて直す → 直した差分と理由を学習データへ
   ↓
[社長] 承認 → 帳簿（承認済み仕訳）
   ↓ 間違いに気づいたら
[AI] 取消＋正しい仕訳の案 → [社長] 承認
```

## 3. 学習のしくみ（R3・R4）

### 3.1 「学習」の意味
- LLM（Claude）のモデルそのものは再学習しない。
- 代わりに、**会社ごとに「直した例」と「ルール」をDBに貯め、読み取りのたびにLLMへ渡す。** 例が増えるほど、同じ店・同じ品目の分類が当たりやすくなる。
- 他社の直した例は混ぜない（会社IDで分ける。07のテナント分離と同じ）。

### 3.2 保存するもの（学習データ）

| テーブル（案） | 中身 |
|---|---|
| `ai_suggestions` | AIが出した候補（日付・金額・店名・分類・自信度）、使ったモデル名、渡した例の版 |
| `ai_corrections` | 人が直した前と後、直した人、**理由（選択式）**：読み間違い／分類違い／私的支出／税率違い／その他 |
| `classification_rules` | 例：「店名に『〇〇石油』→分類『燃料』」。直しが同じ形で3回続いたら、ルール案を出し、人が承認したら有効にする |

### 3.3 間違いを「戻す」
- 承認前の下書き：そのまま直すだけ。
- 承認済みの仕訳：これまでどおり**直接は書き換えない**（08の不変条件）。AIが「取消の仕訳＋正しい仕訳」の案を作り、社長が承認する。
- AIは確定しない。確定のハンコは必ず人が押す（09のK15と同じ）。

### 3.4 dlab の知見の当て方
| 知見 | 設計 |
|---|---|
| 間違いは理由まで書くと、次に同じ間違いを防げる。犯人探しではなく、次にやることを1つ決める（修正速度を上げる技術） | 直した理由を選択式で残す。同じ理由が続いたらルール案を出す。誰が間違えたかは集計しない |
| AIに同じミスを繰り返させないには、作業前の指示と作業後の確認を整える | 作業前：会社のルールと直した例をLLMに渡す。作業後：小計＋税＝合計、税率、通帳の明細・現金との突き合わせで自動検査 |
| AIの間違いを人が見抜くのは難しい | 自信の低い欄、明細と合わない欄だけ色を付けて見せる。全部を目で確かめさせない |
| 最終判断のハンコは人間が持つ（AIへの権限委譲で本番データを失った事故の教訓） | AIは下書きと案まで。本番DBの削除権限はAIにも開発者にも渡さない |

## 4. 写真を1か月で消す（R5）— 先に決めること

**決定（2026-10-23）：写真は30日で消す。正本は紙の領収書で保存し、アプリには読み取った全文をテキストで残す。** 紙の保存方法は税理士と確認する。

- 注意：**テキストだけでは法律上の原本の代わりにならない可能性が高い**（電子保存は画像での保存が前提）。テキストは「探す・確かめる」ための記録として扱い、紙は捨てない。

- 法人の帳簿書類（領収書を含む）には保存期間がある（原則7年。国税庁「帳簿書類等の保存期間」で確認する）。
- 写真を消すなら、**紙の領収書を保存する**ことが前提になる。アプリの写真は「入力のための一時データ」という扱いになる。
- 写真を正本として保存し、紙を捨てたい場合は、電子帳簿保存法の要件を満たす保存が必要になる。その場合は写真を消せない。
- **変更**：09設計書では、証憑を長く保存し、承認済み記録の根拠は消せない設計だった。30日削除を採用するなら、「正本は紙、アプリの写真は30日の一時データ」と書き換える。

### 情報漏えいについて（両面提示）
- 写真を消すことで、漏れて困るものは**減る**。ただし**なくなりはしない**。
  - DBには金額・店名・日付が残る（これは帳簿そのもの）。
  - LLMに写真を送るので、外部（Anthropic）にもデータが渡る。扱いは §4.1 のとおり確認した。
  - バックアップにも写真が残るので、バックアップの保持期間も30日に合わせる。
- 消す処理は毎日1回、キューで自動実行する。消したことは監査記録に残す。

### 4.1 Anthropic の規約の確認結果（2026-10-23に確認）
| 確認したこと | 内容 | 出典 |
|---|---|---|
| 学習に使われるか | 使われない。「Anthropic may not train models on Customer Content from Services」 | [Commercial Terms of Service](https://www.anthropic.com/legal/commercial-terms)（2025-06-17発効）B節 |
| 出力の権利・機密 | 出力は利用者のもの。入力と出力は利用者の機密情報として扱う | 同 B節・E節 |
| 保存期間（Opus 5.5） | 会話内容（送った写真と出力）は既定では保存しない。30日保存が必須なのは Fable・Mythos 系（Covered Models）だけ | [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) |
| 例外 | 不正利用の自動検知に引っかかった場合は最大2年、法律上必要な場合は保存されうる | 同「Retention regardless of arrangement」 |
| 保存されてしまう機能 | Files API（消すまで保存）、Batch処理（29日）、Console の playground | 同 feature eligibility |

注：プライバシーセンターの古い記事には「API の入出力は30日以内に自動削除」とある。新しいドキュメントの記述と食い違うため、本番前にもう一度確認する。

**設計への反映**
- 写真は Messages API に**その場で直接**（base64）渡す。Files API と Batch 処理は使わない。
- Console の playground に実際の領収書を貼らない（保存対象になる）。
- 構造化出力のスキーマ（JSONの型定義）には、店名や金額などの実データを書かない（スキーマは24時間キャッシュされる）。
- 使うのは自社のAPIキーだけ。キーはサーバーの環境変数に置き、画面（ブラウザ）には渡さない。

## 5. 手持ち現金（R1）

- 口座の種類に「現金」を足す（08の `bank_accounts.kind` に `cash` はすでにある）。
- 現金で払ったレシートは、ほかと同じく撮って送る。
- 通帳と違って明細データがない。なので**月末に手元の現金を数えて1回だけ残高を入れ**、帳簿の残高と比べる。差があれば締めナビに出す。
- 銀行から引き出した現金は、費用ではなく「口座から現金への振替」として扱う。通帳の明細に「引き出し」が出たら、振替の候補を作る。
- 両面提示：現金は「数える」作業が月1回残る。ここはゼロにできない。

## 6. テスト環境から本番へ（R7）

### 6.1 3つの環境
| 環境 | 使うデータ | LLM | 目的 |
|---|---|---|---|
| 開発（自分のPC、Docker） | 架空のデータ（seed） | 呼ばない。決まった答えを返す偽物に差し替える | 作る・自動テスト |
| テスト（ステージング） | 架空のデータ＋個人情報を消した領収書 | 本物を呼ぶ（テスト用のAPIキー、上限を設定） | 読み取り精度と学習の効果を測る。本番と同じ手順で更新を試す |
| 本番 | 実データ | 本物を呼ぶ（本番用のAPIキー） | 丹内建機で使う |

- 本番の実データは、テスト環境に持ち込まない（07の決定どおり）。
- APIキー・DBのパスワードは環境ごとに分け、リポジトリには置かない（`.env` は Git の管理外。`.gitignore` 済み）。

### 6.2 本番に出す手順（毎回同じ）
1. 開発環境で Pest のテストが全部通る
2. GitHub に push → GitHub Actions でテストが自動で走る
3. テスト環境に自動で反映し、手順書のチェックリストで動作を確かめる
4. 本番の前にバックアップを取る
5. 本番に反映（DBの変更は migration で。戻す手順も先に書いておく）
6. 反映後の確認（ログイン・送信・承認・締めナビ）

ticket-app で作った「main への push でテストのあと VPS へデプロイする仕組み」を使い回す（不自由発想：今あるものを使い回す）。

### 6.3 学べるようにする
- `docs/runbook.md` に、環境の作り方・更新・戻し方・バックアップからの復元を、自分の言葉で書く。
- 本番で何かあったら、まずテスト環境で再現して直す。直した手順は runbook に足す（修正速度を上げる：失敗を手順に変える）。
- 本番への反映は人が承認してから。AIのツールには本番の削除権限を渡さない。

## 9. これまでの資料との違い

- 発表資料の付録16・17は「当面OCRは使わない」。今回、**テスト環境でLLMの読み取りを試し、合格したら下書きの初期値に使う**方針にした。これは付録17の「試す → 入れる」と同じ順番なので、矛盾はしない。ただし「OCR」を「LLMの読み取り」に言い換える。
- 09設計書の「証憑を長く保存する」は、「正本は紙。アプリの写真は30日の一時データ、読み取ったテキストは仕訳と一緒に保存」に書き換える。
