## 1. デモ版で LLM にやらせること

すべて Claude Opus 5.5（`claude-opus-5-5`）を、構造化出力（JSON スキーマ）で呼ぶ。1回の呼び出しを「AIの実行（ai_runs）」として全部記録する（§4）。

| # | タスク（task） | 入力 | LLM の出力 | 使う画面 |
|---|---|---|---|---|
| L1 | `read_receipt` 読み取り | 写真 | 全文テキスト、日付、店名、合計金額、税率ごとの金額、登録番号、各欄の自信度（0〜1） | 送る（送った直後に裏で） |
| L2 | `journalize` 仕訳 | L1 の結果＋会社の分類・勘定科目・口座の一覧＋**直した例（最近20件）** | 分類、借方・貸方の行（科目・金額）、摘要、理由（なぜその分類か）、自信度 | 下書き |
| L3 | `check_entry` 検算 | 仕訳の行 | 借方合計・貸方合計・一致するか・気になる点（重複の疑い・私的支出の疑い） | 承認 |
| L4 | `monthly_summary` 月の集計 | その月の承認済み仕訳（JSON） | 勘定科目ごとの合計、分類ごとの合計、口座ごとの増減、前月との比較のコメント | 締めナビ・Excel |
| L5 | `close_check` 締めの確認 | その月の原資料・仕訳・現金の残高 | 「あと何件」と、その内訳（未処理・下書き・差）、締めてよいかの意見 | 締めナビ |
| L6 | `correct_entry` 直す案 | 承認済みの仕訳＋人の指摘（文章） | 取消の行と正しい仕訳の案 | 仕訳の詳細（時間があれば） |

### 1.1 LLM に任せないもの（デモでも守る）
「計算」ではなく **安全と順番の約束** なので、コードで守る。どれも数行で済む。

| 守ること | 理由 |
|---|---|
| 他社のデータは見えない（会社から引く・404） | 情報漏えいはデモでも許されない |
| 人が承認するまで「承認済み」にならない | 「AIは下書きまで、確定は人」を見せるのがデモの要 |
| 写真は30日で消える | 決定済み（10 D1） |
| ログイン・2段階認証 | 本番のサーバーに置くため |
| LLM の出力を JSON スキーマで検証し、形が違えば保存しない（やり直しは1回まで） | 壊れたデータを貯めないため |

**LLM の計算が合っているかは、デモではコードで判定しない。** 代わりに、人が直した結果と一緒に記録し、Python編で規則の答えと比べる（§4.3）。画面では LLM が出した数字に「AIの計算」の印を付ける。

## 2. Excel への出力（できます）

承認済みの仕訳を、月ごとに **.xlsx** でダウンロードする。ファイルを作るのは PHP のライブラリ（`phpoffice/phpspreadsheet`）。**載せる数字（集計）は L4 の LLM の出力をそのまま使う。**

| シート | 中身 | 数字の出どころ |
|---|---|---|
| 仕訳帳 | 日付・摘要・取引先・借方科目・借方金額・貸方科目・貸方金額・分類・作った人・承認した人・「AIのまま／人が直した」 | 承認済みの仕訳（DB） |
| 月次集計 | 勘定科目ごと・分類ごとの合計、口座ごとの増減、AIのコメント | **L4（LLM）** |
| 原資料 | 送った日・送った人・状態・読み取ったテキスト（写真は入れない） | DB |
| AIの記録 | その月の AI の実行回数・直された回数・直された欄と理由 | ai_runs・ai_corrections |

- ファイル名：`丹内建機_帳簿_2026-10.xlsx`。シートの見出しと列幅を整え、金額は「#,##0」の書式。
- サーバーにファイルを残さない（その場で作って返す）。ダウンロードしたことを監査記録に残す。
- **決定（10/24）：新しいファイルとして出す。** 既存の Excel の形には合わせない。
- 「月次集計」シートには、分類ごとの円グラフと口座の増減の棒グラフを入れる（PhpSpreadsheet のグラフ機能）。開いた瞬間に「帳簿」ではなく「経営の数字」に見えるようにする。

## 4. 学習データ（Python編へ渡すもの）

### 4.1 テーブル
| テーブル | 主な列 | 中身 |
|---|---|---|
| `ai_runs` | id, company_id, task（L1〜L6）, subject_type/id, model, prompt_version, input（JSON。**写真は入れず、読み取ったテキストと参照したID**）, output（JSON）, valid（スキーマに合ったか）, input_tokens, output_tokens, latency_ms, error, created_at | LLM を呼んだ記録すべて |
| `ai_corrections` | id, company_id, ai_run_id, journal_entry_id, field（date / vendor / amount / category / debit_account / credit_account / line_amount / summary_amount など）, before, after, reason, **kernel**, corrected_by, created_at | 人が直した前後と理由 |
| `ai_feedback` | id, company_id, ai_run_id, rating（good / bad）, comment, user_id | 締めの確認・集計への「合っている／違う」 |

**kernel（失敗の核）**：直したときに、間違いの型を短い文字列で残す。例：`vendor:〇〇石油 → category:燃料`、`tax:8%→10%`、`amount:小計を合計と読んだ`。同じ kernel が何回出たかを数えれば、Python編で規則にする候補が分かる（§6 の dlab の知見）。

### 4.2 書き出しの形
- 「学習データを書き出す」で、会社ごと・期間ごとに **JSONL**（1行1件）を返す：`ai_runs.jsonl`、`ai_corrections.jsonl`、`journal_entries.jsonl`（承認済みの正解）。
- 写真・個人の名前・メールアドレスは入れない（作った人は `user_id` のハッシュ）。

### 4.3 Python編でやること（予告）
1. 承認済みの仕訳を「正解」とし、L2 の仕訳・L3 の検算・L4 の集計を Python で計算し直して、**LLM の答えとの差（正解率・ずれた金額）**を項目ごとに出す。
2. kernel の多い順に、規則（店名→分類、税率の判定、合計の検算）を書き、規則で直せる割合を測る。
3. 規則で決まるものは Python に、決まらないもの（読み取り・あいまいな分類）だけ LLM に残す流れを作る → 実務版（01〜03）へ。

## 5. 技術の追加（02 からの変更）

| 項目 | 内容 |
|---|---|
| LLM の呼び出し | `app/Services/Ai/ClaudeClient`（Laravel の HTTP クライアントで Messages API）。タスクごとに `app/Services/Ai/Tasks/ReadReceipt` など。プロンプトは `resources/prompts/{task}.md`、版は `prompt_version` |
| 非同期 | 送った直後の L1→L2 はキュー（`database` ドライバ）で実行し、画面は `wire:poll` で待つ。本番は `queue:work` を supervisor で常駐 |
| 開発・テスト | `AI_DRIVER=fake` で `FakeClaudeClient`（タスクごとに決まった JSON を返す）。自動テストで本物は呼ばない |
| 写真の送り方 | Messages API にその場で base64。Files API・Batch は使わない（10 §4.1） |
| 費用の上限 | Anthropic のコンソールで月の上限を設定。アプリでも1社1日の実行回数に上限（例：200回）。超えたら手入力に切り替わる |
| Excel | `phpoffice/phpspreadsheet` |
| 失敗したとき | 30秒で打ち切り。L1・L2 が失敗しても原資料は残り、人が手で下書きを作れる |

### 5.1 費用と上限

#### 料金（Claude Opus 5.5、2026-10 時点）
入力 $4 / 100万トークン、出力 $20 / 100万トークン（思考のトークンも出力として数える）。

#### 1枚あたりの見積もり（中央値）
| タスク | 入力 | 出力 | 費用 |
|---|---|---|---|
| L1 読み取り（写真1枚＋指示） | 約5,000 | 約1,500 | 約 $0.05 |
| L2 仕訳（直した例20件込み） | 約4,000 | 約1,000 | 約 $0.04 |
| L3 検算 | 約1,000 | 約300 | 約 $0.01 |

#### 上限の決め方（dlab の知見）
見積もりは自分の頭でせず、「中央値」と「8割の確率で収まる範囲」を出し、予備費を足す。平均の超過幅は62%（[失敗を徹底的に潰す戦略的悲観術](https://daigovideolab.jp/play/D2SQ2WUQq4MZCYBFlMeo?t=3334)）。AI の利用料は「人を雇うより高くつく」と大企業でも見直しが起きている（[AI News 2026-05-28](https://daigovideolab.jp/play/GuwY43gPa5U8kswkjNL4)）ので、最初から上限を置く。

| 使い方（デモ用の1か月） | 枚数 |
|---|---|
| 開発中の動作確認 | 50 |
| デモの練習（3分×10回） | 50 |
| 本番のデモと予備 | 20 |
| 合計 | 120枚 × $0.10 ＝ **中央値 約 $12** |
| 8割の範囲（超過62%を見込む） | 約 $20 |

**決定（案）：月の上限 $20（約3,000円）。** Anthropic のコンソールで上限を $20 にし、$10 で通知。アプリでも1社1日100回まで（超えたら手入力に切り替わり、画面に「今日のAIの上限に達しました」）。1日目の実績（ai_runs のトークン数）で見積もりを測り直す（[タイムトライアル](https://daigovideolab.jp/play/jmv0vTgatOuKJfeKWT5I?t=1343)）。

## 6. dlab の知見の当て方

| 知見 | 設計への当て方 |
|---|---|
| 失敗は出来事ではなく「カーネル（核）」を記憶すると、類似の場面で使える（[失敗経験を活かす方法](https://daigovideolab.jp/play/1435421238)） | 直した記録に `kernel`（間違いの型）を残し、同じ型の回数を数える（§4.1） |
| 修正の速さが成長を決める。間違いは理由まで書き、次にやることを1つ決める（[修正速度を上げる7つの技術](https://daigovideolab.jp/play/012GmqxNVkCMqMtCgG9H)） | 直すときに理由を選ばせ、直した例を次の L2 に渡す。誰が間違えたかは集計しない |
| 見積もりは甘くなる。約7割の案件が予算を超え、平均の超過幅は62%（[失敗を徹底的に潰す戦略的悲観術](https://daigovideolab.jp/play/D2SQ2WUQq4MZCYBFlMeo?t=3334)） | LLM を中心にしたぶん、手で作る計算は減った。かわりに Excel と AI の記録が増えたので、時間割を組み直して削る順番を先に決める（§8） |
| AI が本番 DB とバックアップを消した事故（[AI News](https://daigovideolab.jp/play/VnZ4H9CbIABZRy1dOoim?t=6993)） | LLM には DB を直接触らせない。LLM は JSON を返すだけで、保存はコード。承認は人 |
| 完了の条件は、テストなどのコマンドで決める（[Claude Opus 4.7 の記事](https://daigovideolab.jp/blog/r80ky4muud8w26msg6m2xd)） | 偽物の LLM で全画面のテストを回し、`/check` が通れば完了 |

### 7.1 考え方

### 7.2 見せ場（5つ）
| # | 見せ場 | 画面の作り |
|---|---|---|
| S1 | **AIが読んでいく様子が見える** | 送ったあと、項目が1つずつ現れる：「店名：〇〇石油 ✓」「合計：3,850円 ✓」「分類：燃料（店名に"石油"があるため）」。右上に処理時間（例：8.2秒）。裏では L1・L2 の出力を `ai_runs` に段階ごとに書き、画面は `wire:poll.500ms` で読む |
| S2 | **2つの画面が同時に動く** | 手元のスマホで送ると、プロジェクターの「ライブ画面」（`/c/{company}/live`、PC 用の大きな表示）に写真 → 読み取り → 仕訳が流れてくる。会場の全員が同じ瞬間を見る |
| S3 | **AIが覚える瞬間** | 1枚目：AIが「消耗品」と出す → 人が「燃料」に直し、理由「分類違い」を選ぶ。2枚目（同じ店）：AIが「燃料」と出し、「前回の修正を覚えています」の印が付く。仕組みは L2 に直した例を渡すだけ（§4） |

| S5 | **数字で締める**（終わり） | AIの記録画面：「AIが作った仕訳 42件のうち、そのまま承認 36件（86%）」「一番多い直し：分類違い」「この記録で、次は Python 編で規則にします」 |

### 7.4 止まらない仕組み（デモの保険）
| 起きること | 備え |
|---|---|
| 会場の電波が弱い | スマホはテザリング、PC は有線か別回線。写真は事前に撮ったものを「写真を選ぶ」から送れる |
| API が遅い・失敗する | **デモ再生モード**：`DEMO_REPLAY=true` のとき、同じ写真（SHA-256 が一致）なら練習で記録した ai_runs の出力を、記録したときと同じ間隔で再生する。画面には「再生」の印を小さく出す（見る人をだまさないため） |
| 時間が足りない | 2:20 の Excel までで終われる順番にしてある。S5 は口頭で1文 |
| 全部だめ | 練習のときの画面録画（3分）を流す |

**デモに使う領収書は架空のもの**（自分で作った、または個人情報を消したもの）。3枚を印刷して持っていく（1枚目と2枚目は同じ店）。

### 7.5 八幡平市の副市長に見せる（決定 10/24）

**場**：PC の画面を大きなプロジェクターにミラーリングし、**ライブ画面（S2）を主役**にする。手元のスマホで撮って送る。

#### 何を持ち帰ってもらうか（1文）
「**地域の家族経営の会社が、レシートを撮るだけで帳簿を作れる。費用は1枚約15円、写真は30日で消え、AIは学習に使わない。**」

### 7.6 画面の流れ（見る人に、動きが途切れず見えるように）

絵コンテ：[mockups/storyboard.png](mockups/storyboard.png)（元は `mockups/storyboard.html`）。

**決まり：プロジェクターには最初から最後までPCの画面を映し、操作の結果はすべてライブ画面に出す。** スマホは「撮って送る」だけに使い、スマホの画面は映さない（小さくて見えないため）。直す・承認するは、PC のライブ画面の上で行う（画面を行き来しない）。

| 4 | 0:30 | — | 分類が「消耗品」と出る（間違い）。仕訳の行ができ、流れに「下書き」が1件増える | — |

#### 動きをはっきり見せるための作り
| 作り | 内容 |
|---|---|
| 状態は1か所 | 送る・読み取り・直す・承認のどれも、`source_records` と `journal_entries` の状態と `ai_runs` の段階に書く。ライブ画面は0.5秒ごとに読み直して描き直す（`wire:poll.500ms`）。スマホから送っても、PC で押しても、同じ画面に出る |
| 段階を細かく出す | L1・L2 の途中で `ai_runs.stage`（受け取り → 読み取り中 → 店名 → 日付 → 合計 → 分類 → 仕訳）を書き、画面はその段階まで表示する。AIの返事は一度に来るので、画面側で1項目ずつ0.4秒の間をあけて出す |
| 変わった所を光らせる | 新しく出た値・変わった値は1秒だけ薄いオレンジの背景にする |
| 待ち時間の表示 | 「AIが読んでいます」に処理時間の秒数を出し、止まって見えないようにする。15秒を超えたら「少し時間がかかっています」 |
| 失敗したら | 30秒で打ち切り、カードに「AIが読めませんでした。手で入れられます」。デモでは再生モードに切り替える（§7.4） |

### 7.7 UIの検証（dlab の知見、10/24）と決まり

当てた知見：AIが作るUIは「コントラストが弱い・タップ領域が小さい・状態（読み込み中・エラー・無効）が抜ける」が起きやすい（[awesome-design-skills の記事](https://daigovideolab.jp/blog/ak1ej6jtmuqgqwsnm9bo55)）。脳は一度に1つしか処理できない（[シングルタスク](https://daigovideolab.jp/play/Pe2dDQ54jeTMLKWxokfc)）。

| # | 見つかったこと | 決まり（実装で守る） |
|---|---|---|
| 1 | 絵コンテの件数が合っていなかった（3件に2枚足して承認3回で0件） | **「あと n 件」＝その月の未処理の原資料＋下書きの仕訳。** コードはこの1つの式だけで数える。デモは「あと1件」から始め、2枚送って3件、承認3回で0件 |
| 2 | ライブ画面に直す・承認のボタンがなかった | ライブ画面の最新の1件の下に、大きなボタン2つ（**E 直す**・**A 承認して次へ**、高さ76px）。キーボードでも押せる。選ばれているボタンには太いオレンジの枠 |
| 3 | 見る所が同時に3〜4か所あった | **今動いている所だけをオレンジの枠で明るく、ほかは薄く（不透明度60%）。** 読み取り中は左、承認の瞬間は「あと n 件」を明るくする |
| 4 | 基準（4.5）に届かない色があった：無効ボタン2.25、「送れました」4.32、「注意」4.47、タブのアイコン1.37 | 文字は4.5以上、アイコン・枠は3.0以上。無効のボタンは白地に点線の枠と濃い文字で「あと3件で押せます」。緑は #1F6B40（5.6）、注意の文字は #9A4508（5.8） |
| 5 | 送る画面の状態が描かれていなかった | **送る画面は6つの状態を描き分ける**：待ち・確認・送信中・送れました・同じ写真です・送れませんでした（[mockups/send-states.png](mockups/send-states.png)） |
| — | スマホの補足の文字が12〜13px | 本文16px以上、補足15px以上、タブの文字14px |
| — | 色や大きさが画面ごとにぶれる | 色・文字の大きさ・余白は、工程0で Tailwind の設定（デザイントークン）に1か所で決め、画面では直接の色指定をしない |

## 9. 正直に言うと（デモ版の限界）

- **LLM は計算を間違えることがある。** 合計や集計がずれても、デモ版ではコードで止めない。数字には「AIの計算」の印を付け、実務には使わない。ずれた記録こそが Python編の材料になる。
- 1回の呼び出しに数秒〜十数秒かかる。送ったあとは裏で動かし、待たせない。
- 呼ぶたびに費用がかかる。月の上限と1日の回数の上限を置く。
- 実在の領収書を本番で読ませるのは、社長の同意メモ（Q7）のあと。デモは架空の領収書で行う。
